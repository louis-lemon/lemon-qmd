# vault-search 앱 관점 리뷰

- 작성: 2026-09-15 · 대상: `docs/design.md` · `docs/LOCAL-RUN.md` §4b · `docs/implementation-plan.md` Track B
- 실사 기준: 이 레포 `feat/workbench-overhaul` (`c3a01fc`), 로컬 설치된 `@tobilu/qmd` 2.8.3 dist (`~/.local/lib/node_modules/@tobilu/qmd`), Electron 39.8.10 실행 파일
- 문서가 `docs/vault-search/`가 아니라 `docs/` 바로 아래에 복사돼 있어 이 파일도 `docs/REVIEW.md`에 둔다.

## 레포 실사 요약

- **스택:** Electron 39.8.10 (내장 Node 22.22.1, `process.versions.modules` = 140) + electron-vite 5 + React 19 + Tailwind 4. pnpm `node-linker=hoisted` (`.npmrc`). 시스템 Node는 22.23.2 (modules 127) — Electron과 ABI가 다르다.
- **번들러:** electron-vite. 메인 프로세스 산출물 `out/main/index.js`는 `jsdom`·`turndown`·`yaml` 등 `dependencies`를 `require()`로 남긴다 — 의존성은 기본으로 external 처리된다. 메인 진입점이 둘(`index`, `embedding-worker`, `electron.vite.config.ts:7-13`).
- **builder:** `electron-builder.yml` — mac `dir` 타깃만 있고 `win:` 블록 없음, `npmRebuild: false`(37행), `asarUnpack`은 `resources/**`·`**/*.node`·`onnxruntime-node/bin/**`(19-24행). 네이티브 리빌드는 `postinstall: electron-builder install-app-deps`(`package.json:17`)가 맡는다. `pnpm.onlyBuiltDependencies`는 `electron`·`esbuild`뿐(98-101행).
- **기존 네이티브 모듈·검색 엔진:** 이미 검색 엔진이 있다. 키워드는 자체 BM25(`src/shared/wiki/search.ts:1-2`, 한중일 2글자 쌍 토큰), 의미 검색은 `@huggingface/transformers` + `onnxruntime-node`로 `Xenova/multilingual-e5-small`을 utilityProcess에서 돌린다(`src/main/embedding/worker-embedder.ts:7-10`, `:41-44`). 모델(129MB)은 빌드 시점에 `scripts/fetch-embedding-model.mjs`로 받아 `extraResources`로 싣고 런타임 다운로드는 없다(`embedding-worker.ts:2`). 인덱스는 `userData/embeddings/<vaultKey>`(`src/main/ipc/search-handlers.ts:33`), e2e는 `EMBEDDING_FAKE=1` 가짜 임베더(`playwright.config.ts:5`).
- **CI 매트릭스:** `.github/` 디렉터리 자체가 없다. CI 없음. 제품 출하 타깃은 macOS arm64 + Windows x64, macOS Intel·Windows arm64 제외(`PRODUCT.md` § Platform, § Out of v1).

| **A. 계약 적합성** — `createStore`를 어디서 실행하나 | **틀림(부분)** — 계약 자체는 맞지만 "메인 프로세스에서 import" 전제는 이 앱 구조와 맞지 않는다 | 앱은 모델 추론을 메인 이벤트 루프 밖 utilityProcess에 격리한다(`worker-embedder.ts:41-44`). 이유가 코드에 남아 있다: ONNX가 232페이지 볼트에서 utilityProcess를 exit 5로 죽였다(`embedding-index.ts:44-46`). llama.cpp abort가 메인에서 나면 앱 전체가 죽는다. `better-sqlite3`는 동기 호출이라 메인에서 돌면 대용량 `update()` 동안 IPC가 멈춘다. `createStore` 인라인 config는 신뢰 게이트를 타지 않는다(qmd `dist/index.js:73-77`, `setConfigSource`→`syncConfigToDb`만 호출) — 이 점은 design §2와 일치 | `embedding-worker.ts`를 `search-worker.ts`로 대체하고 그 안에서 `createStore`. 메인은 `worker-embedder.ts`와 같은 id 매칭 IPC로 `update/embed/search/searchLex/status`만 중계. 렌더러 계약(`APP_CHANNELS.searchWiki`, `EmbeddingStatus`)은 유지 가능. `dbPath`는 기존 `indexDir(vaultDir)` 규칙 재사용 |

| **C. Windows** — CI 매트릭스, 프리빌트 기본값 | **틀림(근거)** — "현재 CI/빌드 매트릭스"가 존재하지 않는다 | `.github/` 없음. `build:win` 스크립트만 있고(`package.json:19`) `electron-builder.yml`에 `win:` 블록이 없다. node-llama-cpp 3.20.0 optionalDependencies에 `win-x64`·`win-x64-cuda`·`win-x64-cuda-ext`·`win-x64-vulkan`·`win-arm64` 프리빌트 존재(qmd `node_modules/node-llama-cpp/package.json:226-241`) — pnpm은 현재 플랫폼 것만 설치하므로 Windows 산출물은 Windows 러너에서 빌드해야 한다. qmd GPU 판정(`dist/llm.js:408-421`): `QMD_FORCE_CPU`는 `false/off/none/disable/disabled/0` 외 어떤 값이든 CPU 강제, 미설정이면 `gpu:"auto"`(CUDA→Vulkan→CPU 순, `:637-650`) | 기본 **CPU**(`win-x64`)로 간다 — 제품 대상이 비개발자 PC라 CUDA 런타임·AMD Vulkan 행 이슈(design §8)를 감당할 수 없다. 워커 진입점에서 Windows면 `process.env.QMD_FORCE_CPU='1'` 고정, GPU는 설정 화면 옵트인(2차). 설치 크기를 위해 `files`에서 `@node-llama-cpp/win-x64-cuda*`·`*-vulkan`·`linux-*`를 제외. CI는 `windows-latest` 1잡 신설, macOS는 PC 수동 빌드(결정 4) |
| **D. 모델·캐시** — XDG 우회 가능성, 첫 실행 다운로드 UI | **확인됨(결정 1로 종결)** — 우회 자체는 되지만 메인 정적 import로는 불가, 다운로드 UI는 동봉 결정으로 불필요 | `MODEL_CACHE_DIR`은 qmd 모듈 로드 시점에 `XDG_CACHE_HOME`을 읽어 고정된다(`dist/llm.js:143-145`). 메인 `src/main/index.ts`는 1-21행 정적 import가 76-77행 `setPath('userData')`보다 먼저 평가되므로 **메인에서 정적 import하면 우회가 안 된다**. 워커 진입점에서 env 설정 후 `await import()`면 된다. `createStore`는 `LlamaCpp`에 `modelCacheDir`을 안 넘긴다(`dist/index.js:82-88`) — design 실사와 일치. 다운로드 진행: `resolveModelFile`에 `{directory, cli}`만 넘겨(`dist/llm.js:277-279`) **SDK 경로엔 진행 콜백이 없다**. node-llama-cpp 자체 `resolveModelFile`은 `onProgress`를 받는다(`dist/utils/resolveModelFile.d.ts:47`). 크기(로컬 캐시 실측): Qwen3-Embedding-0.6B-Q8 610MB, Qwen3-Reranker-0.6B-Q8 610MB, **쿼리 확장 1.7B q4 1,223MB** — 합 2.4GB. `store.search({query})`는 BM25 강신호가 없으면 확장 모델을 부른다(`dist/store.js:4344-4354`) → 프롬프트의 "~1.3GB"는 확장 모델을 빼고 센 값이다. 제품 원칙과 충돌: "Semantic search runs a bundled local model and works offline", "install to first approved page ≤10 min", "Nothing runs in the background"(`PRODUCT.md`) | 결정 1: 임베딩 모델 동봉. `scripts/fetch-embedding-model.mjs`를 GGUF용으로 바꿔 `resources/models/`에 node-llama-cpp 파일명 규칙(`hf_Qwen_Qwen3-Embedding-0.6B-Q8_0.gguf`)으로 두고, 워커 진입점이 `XDG_CACHE_HOME`을 그 부모로 잡은 뒤 동적 `import()`. 모델 파일이 없으면 `searchLex`만으로 동작하고 사유 표시(`search-handlers.ts:22-24` 경로 재사용) |
| **E. 질의 경로** — raw 한국어 그대로 vs 앱이 lex/vec/hyde 생성 | **확인됨** — raw 질의. 앱은 LLM으로 질의를 만들지 않는다 | 엔진은 사용자 구독의 `claude`/`codex` CLI 서브프로세스이고(`src/main/engine/create-engine.ts`), "The LLM only synthesizes", "Nothing runs in the background… subscription usage is never spent without the user knowing", "Local LLMs: out of v1"(`PRODUCT.md`). 검색은 150ms 디바운스로 키 입력마다 돈다(`src/renderer/src/views/search-view.tsx:1-2`) — 키 입력당 CLI 호출은 비용·지연 모두 불가. 따라서 **Q1/I1의 가치는 앱 경로에서 그대로 유효**하다. 단 SDK 기본 `search({query})`는 qmd 내장 1.7B 확장 모델(영어 파인튜닝, design §3이 "한국어엔 쓰지 않는다"고 한 것)을 조건부로 호출한다 — 앱이 아무것도 안 하면 그 모델이 돈다 | 앱은 `search({queries:[{type:'lex',query:raw},{type:'vec',query:raw}], rerank})`의 **structured 경로**를 쓴다(`dist/index.js:104-116`, 확장 모델 미호출). 결정 2·3: 키 입력 = `searchLex`, Enter/버튼 = lex+vec RRF, `rerank:false` 고정. 리랭커·확장 모델은 v1 제외 |
| **F. 벤치 연결** — 골드셋을 앱 CI 회귀 가드로 | **미결정(질문)** — 지금은 못 돌린다, 만들면 lemon-qmd CI가 맞다 | 앱 CI가 없다. `qmd bench`는 CLI(`dist/bench/`)이고 vector/hybrid/full 백엔드는 모델(≥610MB) 다운로드를 요구한다. 골드셋 정본은 2nd-brain, 복사본은 lemon-qmd(design §3) — 앱 레포엔 픽스처가 없다. 앱 단위 테스트는 시스템 Node ABI라 Electron용 `better-sqlite3`를 못 연다(B①) | 벤치 회귀는 design대로 lemon-qmd CI 소유. 앱 CI는 (1) SDK 스모크 — 픽스처 vault로 `searchLex('검색') ≥ 1`을 **`ELECTRON_RUN_AS_NODE=1 electron`** 또는 Playwright e2e로(ABI 문제 회피), (2) 패키징 스모크 — `build:unpack` 후 앱을 띄워 `searchLex` 응답 확인. 모델이 필요한 수치는 앱 CI에 넣지 않는다 |
| **G. 범위 밖 확인** — §7이 앱에 떠넘긴 것 중 감당 못 할 것 | **틀림(부분)** — 네 가지가 제품 계약과 부딪힌다 | (1) 키 입력당 하이브리드+리랭크는 불가 — 검색 UI를 "입력=키워드, 제출=전체"로 바꿔야 한다(`search-view.tsx:1-2`). (2) 2.4GB(또는 1.2GB) 첫 실행 다운로드 vs "install to first page ≤10 min"(`PRODUCT.md` § Product Purpose). (3) 리랭커·확장 모델은 LLM 추론이다 — "Local LLMs: out of v1"(`PRODUCT.md` § Out of v1)과 충돌, 임베딩 모델만 명시 허용됨. (4) Windows 빌드·CI 러너가 없다 — "앱 레포 책임"(design §8 마지막 행)이라 적혀 있지만 러너·서명·설치본 형식이 미결정. 컬렉션 `wiki/`만 색인(§7)은 앱 `searchable()`과 일치(`src/main/wiki/wiki-service.ts:126-127`). 메모리: 임베딩+리랭커 상주 1.2GB(5분 비활성 후 해제, `dist/index.js:86-87`)는 비개발자 노트북 기준 검증 필요 | (1)은 결정 3, (2)는 결정 1, (3)은 결정 2로 종결. (4)는 lemon-qmd B0의 windows 잡이 앱 빌드 조건(Electron 39, `install-app-deps`, asarUnpack 목록)을 그대로 쓰게 한다(HANDOFF의 "라이브러리 CI가 앱 빌드를 대변" 원칙) |
| **H. 문서 오류** | **틀림(근거)** — 4건 | ① design §2 "2nd-brain: 검색 엔진 없음(INDEX.md + rg)"은 vault 레포 기준으론 맞지만 **앱에는 이미 BM25+의미 검색이 있다**(`search.ts:1-2`, `worker-embedder.ts:7`). design §7·§8 어디에도 기존 엔진(onnxruntime·transformers·129MB e5 모델·인덱스 포맷·`EMBEDDING_FAKE` e2e)의 **교체·마이그레이션**이 없다 — 앱 작업 범위가 "통합"이 아니라 "교체"다. ② HANDOFF D "~1.3GB: Qwen3-0.6B + 리랭커" — 실측 610+610=1.2GB이고, SDK 기본 `search`는 확장 모델 1,223MB를 추가로 받는다(`dist/store.js:4352-4354`). design §3 "쿼리 확장… Opus가 lex/vec/hyde 직접 작성"은 CLI 경로 설명이라 앱 경로엔 적용되지 않는다. ③ LOCAL-RUN §4b `await store.embed?.()` — `embed`는 옵셔널이 아니다(qmd `dist/index.d.ts:195`). ④ LOCAL-RUN §4b "import 전에 메인 프로세스에서 `process.env.XDG_CACHE_HOME` 설정" — 메커니즘은 맞지만(`llm.js:143`) 이 앱 메인은 정적 import라 실행 순서상 불가(`src/main/index.ts:1-21` vs `:76`). "워커 진입점에서 env 설정 후 동적 import"로 고쳐야 한다. 확인된 것: node-llama-cpp Windows 프리빌트 목록, better-sqlite3 Electron 리빌드 필요, SDK 경로 신뢰 게이트 없음, `StoreOptions`에 `modelCacheDir` 없음(`dist/index.d.ts:108-116`) — 모두 design §2와 일치. qmd 대안 재검토 사유 없음 | design.md 정정 4로 ①②④ 반영, §4b 스니펫은 ③과 structured 경로(E)로 갱신 |
